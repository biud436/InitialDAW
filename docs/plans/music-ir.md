# I. Music IR

> 작성일: 2026-10-09. 계기: Music IR 계획서. 곡을 한 번 만든 뒤 고칠 때마다 생성기와 JSON 을 처음부터 다시 읽어
> 곡의 짜임을 다시 세우는 비용을 줄인다. 작곡 엔진과 첫 생성은 바꾸지 않는다.

## 1. 목표

작곡 생성기가 이미 아는 뜻(구간, 화음표, 트랙의 역할, 주제와 그 쓰임, 구간 사이의 관계, 트랙 사이의 의존)을 생성할 때 곡 곁에 남긴다.
에이전트는 그 곁 파일로 곡 전체에서 구간, 트랙, 음표, 생성기의 코드 줄까지 좁혀 가며 조회하고, 고친 결과가 뜻한 마디와 트랙 안에
머물렀는지 검사한다. 곡 JSON 과 렌더러는 그대로 둔다.

## 2. 조사

| 항목 | 찾은 것 |
|---|---|
| 곡 JSON 스키마 | 최상위와 트랙이 `additionalProperties: false` 다. 파서도 모르는 키를 오류로 막는다. 열린 자리는 최상위 `metadata`(객체)와 `comment`(문자열)뿐이다. 트랙 이름이 스템 이름이고 사이드체인이 이름으로 가리킨다 |
| 생성기 | 곡마다 따로인 `compose.py`. 모든 음과 컨트롤러 점이 `Part.add`, `Part.lane` 을 지난다. 구간 시작은 `S` 사전, 화음표는 `PLAN`/`CHART` 와 `CH`(구성음, 베이스), `segments()` 가 (시작 박, 길이, 화음)을 준다. 선율은 `THEME_*` 같은 데이터, 트랙은 `make_parts()` 의 키(`melody`, `vln`), 반주는 `clear_voice()` 가 선율과 부딪는 음을 옮긴다, 세기는 `LEVEL` 곡선 |
| 저장 | `json.dump(data, f, ensure_ascii=False, indent=1)` 한 곳. 앱은 `writeJson` 으로 모르는 필드와 키 순서를 지키며 저장한다 (숫자 표기는 다를 수 있다) |
| 렌더링 | `music-render render` (스템, 리포트), `realtime --from --seconds --output` 이 구간만 렌더링한다 (같은 트랙 사슬). 휴머나이즈 시드는 트랙 이름에서 나와 다른 트랙을 고쳐도 한 트랙의 연주는 그대로다 |
| 시험 | CTest (unit, cli, app_*), 명령행 시험은 Python 의 작은 `check()` 틀 |
| 다시 생성 | 8곡을 지금 생성기로 다시 돌려 보니 「녹슨 날개」 두 판과 「눈 덮인 왕국」의 JSON 이 커밋된 것과 다르다. 2026-10-09 에 보정표를 다시 만든 뒤 다시 생성하지 않았다 (벨로시티와 CC11 만 다르다). 「녹슨 날개」 생성기는 CC11 에 127.66 을 써서 `validate` 를 통과하지 못했다 (127 에서 자르게 고쳤다, 커밋된 JSON 은 그대로) |

재사용한 것: `S`, `segments()`, `CH`, 주제 데이터, `make_parts()` 의 키, `Part.add`/`Part.lane`, 엔진의 `validate` 와 구간 렌더.
바꾼 최소 파일: 생성기 두 개(import 한 줄, `trace` 두 곳, `describe()`, `save` 한 줄), `CMakeLists.txt`(시험 등록). 엔진, 앱, 곡 스키마는 그대로다.

## 3. 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 위치 | 곁 파일 `<곡>.ir.json` (생성기가 곡 JSON 과 함께 쓴다) | 아래 표 |
| 원본 | 음표, 화음표, 선언한 뜻의 원본은 `compose.py`. 곡 JSON 과 IR 은 생성 결과다. IR 은 손으로 고치지 않는다 | 뜻을 음표를 만드는 코드 곁에 두어야 함께 고쳐진다 |
| 앱 편집 지키기 | IR 에 생성기 출력의 지문을 남긴다. 디스크의 JSON 이 그 지문과 다르면(앱에서 저장) 생성기가 덮어쓰지 않고 다른 트랙 x 구간을 알린다. `MUSICIR_FORCE=1` 은 덮어쓰되 지금 파일을 `build/music-ir/backup` 에 남긴다 | 생성기를 다시 돌리면 앱 편집이 조용히 사라지던 문제 |
| 옮겨 심기 | `apply` 는 디스크의 JSON 이 생성기 출력과 이미 다르면, 생성기의 새 출력에서 대상 칸(트랙 x 구간)의 음표와 레인 점만 옮겨 심는다 | 앱 편집과 보정표 차이를 지키면서 생성기로 한 부분을 고친다 |
| 참조 | 곡 id(폴더 이름), 구간 id(`S` 의 키), 트랙 id(`make_parts` 의 키, JSON 이름과 짝), 동기 id, 코드 자리 id(함수, 문장, 같은 문장의 순번의 해시). 범위는 박. 줄 번호는 저장하지 않고 조회할 때 문장으로 찾는다 | 트랙 이름이 바뀌어도(앱) id 는 남고, 지문으로 새 이름 후보를 준다. 줄 번호는 함수 하나만 끼워도 다 밀린다 |
| 출처 | 생성기가 선언한 것(기본), 곡 데이터에서 잰 것(`cells`, 사이드체인 의존, `derived`), IR 이 없는 곡에서 짐작한 것(`origin: inferred`, `confidence`, `basis`) | 확실하지 않은 뜻을 사실처럼 적지 않는다 |
| 에너지 | 선언: 의도 1~5, 흐름(오름, 정점, 빠짐 등), 화성적 긴장 1~5. 잰 값: 음표 밀도, 쉬지 않는 트랙 수, 벨로시티 평균, 음역, 화성 리듬. 따로 보인다 | 에너지를 소리 크기로 환산하지 않는다 |
| 화성 | 생성기의 화음표를 그대로 적는다(박, 길이, 이름, 구성음, 베이스). 로마 숫자는 선언한 글이다. 추론한 IR 은 화성을 적지 않는다 (조성 후보만 상관값과 함께) | 화성 분석은 후순위 |
| 주제 | 동기의 음(박, 길이, 높이)과 쓰인 자리(트랙, 마디, original, transposed, octave, partial, varied)를 선언한다. IR 을 쓸 때 실제 음과 맞춰 일치율을 잰다 | 선언이 낡으면 일치율이 떨어져 드러난다 |
| 의존 | 선언(화음표를 따른다, `clear_voice` 로 선율을 피한다), 곡 데이터(사이드체인), 코드 공유(이 칸을 만든 문장이 부른 도우미 함수와 대문자 데이터 이름을 다른 구간도 쓰는가) | 수정 영향 범위. 「유리 회로」의 `THEME_A1` 처럼 같은 데이터가 앞 구간에도 쓰이는 것을 고치기 전에 알린다 |
| 조회 단계 | 1 `overview`, 2 `section`, `tracks`, `deps`, `compare`, `harmony`, `motifs`, 3 `notes`, `source`. 모두 `--json` | 작은 데서 시작해 필요할 때만 넓힌다 |
| 고치기 | `plan` 이 대상과 보호를 정하고 지금 생성기 출력과 디스크의 JSON 을 떠 둔다. `verify` 가 고친 생성기를 임시 폴더(`MUSICIR_OUT`)에서 돌려 칸마다 견준다. `apply` 가 쓴다 | 디스크의 곡을 건드리지 않고 검사한다. 보정표 차이처럼 이미 있던 차이를 고친 결과와 섞지 않는다 |
| 검사 규칙 | 보호 트랙의 모든 칸과 설정, 화음표, 대상 밖의 칸, 곡 설정, 허락한 종류(notes, cc, settings, new-tracks), 대상 칸의 화성 트랙이 화음 구성음을 지키는가(0.9), 새 IR 의 참조 무결성, `music-render validate`, 선율과 단2도와 단9도로 부딪는 음이 늘었는가(주의) | 계획서 9절의 보호 조건 |
| 실패 | IR 을 만들다 실패해도 곡 JSON 은 이미 썼다. IR 에는 오류와 지문만 남는다. `MUSICIR_OFF=1` 이면 IR 없이 예전처럼 쓴다 | 렌더링을 IR 때문에 멈추지 않는다 |
| 언어와 자리 | Python, `tools/musicir/` 와 `tools/music-ir.py` | 생성기와 같은 언어이고 빌드가 없다. 엔진은 IR 을 몰라도 된다 |
| 부분 렌더 | 엔진의 `realtime --from --seconds --output` 을 쓴다. `section` 이 그 구간의 명령을 적는다 | 렌더러는 고치지 않는다 |

곁 파일과 곡 JSON 안에 넣기를 견준 표:

| 기준 | 곡 JSON 안 (`metadata` 나 새 키) | 곁 파일 (택함) |
|---|---|---|
| 기존 JSON 호환 | 새 키는 엔진의 파서와 스키마를 고쳐야 한다. `metadata` 는 열려 있지만 앱이 저장할 때 IR 이 곡과 함께 옛것으로 남는다 | 곡 JSON 이 바이트까지 같다 |
| 구현 복잡도 | 엔진(C++)과 앱을 함께 고친다 | Python 도구 하나 |
| 생성기와의 연계 | 같다 (생성기가 쓴다) | 같다 |
| 데이터 중복 | 음표가 곁에 있어 지문이 필요 없다 | 지문(해시)만 두고 음표는 두지 않는다 |
| 참조 무결성 | 앱이 음표를 고쳐도 IR 을 모른다 | 지문으로 바뀐 칸을 칸 단위로 찾는다 |
| 부분 수정 | 같다 | 대상 칸만 옮겨 심기 |
| 스키마 확장 | 곡 스키마와 함께 버전을 올린다 | IR 스키마(`tools/musicir/music-ir.schema.json`)만 |
| 컨텍스트 | 2만 줄 넘는 곡 JSON 안에 뜻이 묻힌다 | 조회 명령이 필요한 부분만 준다 |

## 4. 쓰는 법

생성기 (본보기 `songs/glass-circuit/compose.py`):

```python
sys.path.insert(0, os.path.join(REPO, "tools"))
import musicir

class Part:
    def add(self, ...):
        ...
        self.notes.append(musicir.trace(note))      # 이 음을 만든 song() 의 문장과 도우미를 적는다
    def lane(self, cc, points):
        ...
        out.append(musicir.trace(pt))

def describe(ir, P):
    ir.song(key="D major", genre="...", summary="...")
    ir.section("p1", "절정 1", S["p1"], S["p2"] - 1, form="climax", energy=5, trend="peak", tension=3,
               purpose="...", progression="...", roman="I - IV - ii - V | ...", aliases=["절정"])
    ir.harmony(segments(1, END - 1), CH, names={"D9": "Dadd9"})
    ir.track("melody", P["melody"].name, "main-melody", note="...")
    ir.motif("theme-a", "주제 A", notes, kind="theme", data="THEME_A1")
    ir.use("theme-a", "melody", S["p1"], how="octave")
    ir.relate("p1", "a1", "restates", "...")
    ir.depends(["pad", "seq"], "melody", "avoids-clash", via="clear_voice", note="...")
    ir.code("LEVEL", "곡의 세기 곡선")

def main():
    musicir.start("glass-circuit")
    P, moved = song()
    ...
    musicir.save(path, data, lambda ir: describe(ir, P))
```

환경 변수: `MUSICIR_OUT=<폴더>`(그 폴더에 쓴다), `MUSICIR_IR_ONLY=1`(곡 JSON 은 두고 IR 만), `MUSICIR_FORCE=1`(덮어쓰기 막기를 넘는다), `MUSICIR_OFF=1`.
「녹슨 날개」의 IR 은 커밋된 JSON 을 바꾸지 않으려고 `MUSICIR_IR_ONLY=1` 로 썼다. 그래서 `check` 가 "JSON 이 생성기 출력과 다름 (IR 을 만들 때부터)"으로 보인다.

명령행은 README 의 Music IR 절과 `tools/music-ir.py --help`.

## 5. 시험

`tools/musicir/tests/test_music_ir.py` (CTest `music_ir`) 가 저장소의 임시 사본(도구와 곡은 복사, 엔진과 music-render 는 링크)에서 82건을 본다.

| 계획서 12절 | 시험 |
|---|---|
| 1. 기존 JSON 호환 | IR 을 붙인 「유리 회로」 생성기의 JSON 이 커밋된 JSON 과 바이트까지 같다. 두 생성기 모두 IR 을 켜고 끈 출력이 바이트까지 같다. 생성한 세 JSON 이 `validate` 통과 |
| 2. 렌더링 유지 | 렌더러는 곁 파일을 읽지 않는다. 곁 파일이 있고 없을 때 `validate` 요약이 같다. 곡 JSON 이 같은 바이트이므로 렌더도 같다 |
| 3. 스키마 | 세 IR 과 추론한 IR 이 스키마 통과, 모르는 역할과 빠진 필드를 잡는다 |
| 4. 조회 정확성 | 별칭(절정), `last:climax`, `family:strings` 해석, 구간의 박과 초(템포 램프를 엔진과 같은 식으로, 「녹슨 날개」 길이가 엔진과 0.02초 안), 칸의 음표 수와 음역이 JSON 을 직접 센 것과 같다, `notes` 가 JSON 그대로, `source` 의 줄 번호가 지금 파일과 같다, `deps` 가 `string_pad` 공유와 `clear_voice` 를 알린다, `compare` 의 화성 같음과 다름 |
| 5. 참조 무결성 | 새 IR 에 오류 없음, 이름을 바꾼 트랙과 새 이름 후보, 실제 음과 맞지 않는 동기의 자리 |
| 6. 낡은 IR | 음표 하나를 고치면 그 칸 하나만(melody @ p1), 트랙 설정만 고치면 설정 칸만, 생성기와 생성기가 읽은 보정표의 변경, 「녹슨 날개」의 생성기 출력과 다른 JSON |
| 7. 부분 수정 범위 | air @ p2 만 고친 생성기가 verify 통과, 바뀐 칸이 air @ p2 하나(음표 +2), apply 뒤 check 통과 |
| 8. 보호 대상 | 선율을 바꾸면, 대상 밖(air @ b)을 바꾸면, 화음표를 바꾸면 verify 실패. 실패한 계획은 apply 하지 않는다 |
| 9. 다시 생성 뒤 편집 보존 | 앱에서 고친 JSON 을 생성기가 덮어쓰지 않고 고친 칸을 알린다. 앱 편집이 있는 채로 plan, verify, apply 하면 편집이 남고 대상 칸만 바뀐다. 「녹슨 날개」에서 바이올린을 더하면 선율과 피아노 트랙이 커밋된 JSON 과 같다 (보정표 차이가 새지 않는다). FORCE 는 백업을 남긴다 |
| IR 실패 | 선언이 틀려도 생성기는 성공하고 곡 JSON 은 같은 바이트, IR 에는 오류와 지문 |
| 10. 에이전트 조회 효율 | 7절 |

## 6. 완료 시나리오: 「녹슨 날개」 마지막 코러스의 현악

요청은 마지막 코러스의 현악을 더 풍부하게 하되 피아노 선율과 코드 진행은 그대로 두라는 것이다. 이 곡의 선율은 클라리넷(2판 오보에)이고
피아노는 동기와 베이스를 맡으므로 선율(lead)과 피아노를 둘 다 보호했다. 저장소의 곡을 바꾸지 않도록 git worktree 에서 했다.

| 단계 | 한 일 |
|---|---|
| 1. 조회 | `overview` 로 `final`(마지막 코러스, 61~76마디)과 현악 네 트랙, `section rusted-wings "마지막 코러스"` 로 화음 18개와 칸마다 잰 값(바이올린 D4~B4 두 음, 비올라 G3~F#4 두 음, 첼로와 콘트라베이스 한 음) |
| 2. 의존 | `deps --section final --track family:strings`: 현악은 화음표를 따르고 바이올린과 비올라는 `clear_voice` 로 선율을 피한다. `string_pad` 는 다른 아홉 구간도 쓴다 |
| 3. 계획 | `plan`: 고칠 문장은 `song()` 744줄 `string_pad(P, fc, cb=True)` 와 747줄 CC1 곡선. 디스크의 JSON 이 생성기 출력과 20칸(2판 31칸) 다르다는 주의 |
| 4. 고치기 | 마지막 코러스 전용 `rich_strings()`: 바이올린과 비올라를 세 음으로, 첼로는 베이스 위에 3음을 더한다. CC1 을 두 마디마다 커졌다 줄며 74마디로 오르는 곡선으로. `string_pad` 는 그대로 |

## 7. 조회 효율 비교 실험

같은 모델의 에이전트 넷에게 고칠 계획만 세우게 했다 (파일은 고치지 않는다). 과제는 「녹슨 날개」의 마지막 코러스 현악(6절과 같은 요청)과
「유리 회로」의 후반부 선율을 더 극적으로 하되 분위기는 지키라는 요청 둘이다. 과제마다 IR 을 쓰는 쪽과 쓰지 않는 쪽(`music-ir.py` 와 `*.ir.json`
을 쓰지 말라고 했다)을 두었다. 채점 기준은 결과를 보기 전에 정했다.

- 「녹슨 날개」 9항목: 61~76마디, 현악 네 트랙, `string_pad` 호출과 CC1 곡선의 줄, `string_pad` 를 다른 구간도 쓴다, `clear_voice`, 두 판이 `song()` 을 함께 쓴다, 커밋된 JSON 이 생성기 출력과 다르다, "피아노 멜로디"가 모호하다, 화음표 보호
- 「유리 회로」 7항목: 후반부 구간(절정 49~64마디), `play_melody` 두 줄, `THEME_A1`/`THEME_A2` 를 앞 구간도 쓴다, `clear_voice` 의 부작용, 화음표 보호, 절정의 옥타브 겹침, 절정이 주제 A 의 재현이라는 관계

| 과제 | 조건 | 토큰 | 도구 호출 | 시간 | 채점 |
|---|---|---|---|---|---|
| 녹슨 날개 | IR 없음 | 130,263 | 24 | 377초 | 8/8 (보정표 차이는 그 트리에 없어 뺐다) |
| 녹슨 날개 | IR | 116,273 | 30 | 289초 | 9/9 |
| 유리 회로 | IR 없음 | 101,830 | 15 | 237초 | 7/7 |
| 유리 회로 | IR | 138,508 | 36 | 419초 | 7/7 |

결과: 이 실험에서 IR 은 분석에 드는 토큰을 줄이지 못했다 (「녹슨 날개」 -11%, 「유리 회로」 +36%). 네 쪽 모두 핵심 함정(함께 쓰는 함수와 데이터,
`clear_voice`, 두 판, 화음표)을 찾았다. 이 결과를 일반화하지 않는다. 까닭으로 보이는 것:

- 조건이 고르지 않았다. 에이전트의 worktree 넷 가운데 셋이 원격의 예전 커밋(64fa127)에서 만들어져 IR 도구와 「유리 회로」가 없었다. IR 쪽 둘은 main 의 도구를 찾아 쓰거나 worktree 를 앞으로 감는 데 호출을 썼다. IR 없는 「녹슨 날개」 쪽은 보정표도 옛것이라 생성기 출력과 JSON 이 실제로 같았다.
- 이 저장소에는 이미 자세한 작곡 기록(`docs/songs/*.md`)과 생성기 머리말(구성, 화성)이 있다. 사람이 쓴 글로 된 IR 이 이미 있었던 셈이다. IR 없는 「유리 회로」 쪽은 main 의 `compose.py` 를 읽어 `describe()` 의 선언도 보았다.
- IR 쪽 에이전트가 더 깊이 갔다. 「유리 회로」 IR 쪽은 plan 을 두 판 세우고 후보 선율로 verify 를 돌려, `clear_voice` 가 시퀀스 음 3개(62마디)를 옮겨 선율만 대상으로 한 계획이 실패한다는 것과 63마디 3박의 D5 가 단9도를 만든다는 것을 실제로 확인했다. IR 없는 쪽은 이것을 짐작으로만 적었다.
- 「녹슨 날개」의 생성기 출력과 JSON 의 차이(보정표)는 IR 쪽만 찾았다 (`check` 와 `plan` 이 알린다). IR 없이 찾으려면 생성기를 사본에서 돌려 견주어야 한다.

IR 이 분명히 줄인 것은 검증이다: 고친 결과가 범위 안에 있는지, 보호한 트랙과 화음표가 그대로인지를 손으로 JSON 을 견주지 않고 한 번에 본다.
6절의 시나리오는 조회부터 쓰기까지 도구 호출 여섯 번이었지만, IR 을 만든 사람이 한 것이라 위 표와 견주지 않는다.
다음에 견줄 때는 모든 조건을 같은 커밋의 worktree 에서, 과제를 늘려(곡 넷 이상, 고치기와 검증까지) 돌린다.

## 8. 한계

- 선언은 생성기를 쓴 사람(에이전트)이 적은 것이다. 일치율로 동기의 자리는 검사하지만, 구간의 목적과 에너지 의도가 맞는지는 검사할 수 없다.
- 코드 자리는 `song()` 의 문장 한 줄(여러 줄 문장은 첫 줄)이다. 도우미 함수 안의 어느 줄인지는 적지 않는다.
- 검사는 곡 JSON 의 칸 단위다. 울림의 꼬리, 마스터 정규화, 버스 효과(리버브)의 이어짐은 렌더해서 잰다.
- 생성기 둘(「유리 회로」, 「녹슨 날개」)만 선언을 붙였다. 나머지는 추론으로 요약한다. 추론한 구간 경계는 짜임(들고 나는 트랙, 밀도)만 본다.
