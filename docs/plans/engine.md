# E. 음악 엔진 (music-render)

> 작성일: 2026-10-05. 권장 모델: Fable 5 (오디오 그래프와 플러그인 호스팅은 상태 버그가 숨기 쉽다).
> 계기: 홍보 영상 음악을 SoundFont로 렌더링한 소리는 미디 느낌이 강했다. 요구 명세
> (사람의 마우스 조작 없이 에이전트가 작곡, 연주 표현, 가상 악기 렌더링, 믹싱, WAV 출력까지 하는 도구).
> Initial2D 저장소의 `engine/`(계획 MU1)에서 만들었고, 2026-10-05 이력째 이 저장소의 `engine/` 으로 옮겨
> DAW 앱([index.md](index.md))의 엔진이 되었다. 아래의 경로는 옮긴 뒤의 것이다.

## 1. 목표

구조화된 데이터를 받아 오디오를 내는 명령행 도구로 시작했다. 그 위에 사람이 쓰는 DAW 앱(`app/`)을 올린다.

```text
Composition JSON → 연주 처리(Performance) → 가상 악기(Sampler, Plugin) → 효과와 믹서 → Master WAV
```

완료의 정의: 에이전트가 JSON 한 벌과 명령 하나로 같은 WAV를 언제든 다시 만들 수 있고(시드 고정), 결과를
`inspect`로 재서(길이, 피크, RMS, LUFS, 클리핑) 고치고 다시 렌더링하는 반복이 가능하다.

## 2. 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 언어와 빌드 | C++20, CMake 3.22 이상 | JUCE 8 요구. 저장소 최상위 CMake 가 JUCE 와 sfizz 를 더하고 `engine/` 이 핵심 라이브러리, 명령행, 테스트를 정의한다 |
| 오디오 프레임워크 | JUCE 8.0.10 (`external/juce`, 받아서 쓰고 커밋하지 않는다) | VST3와 AU 호스팅, WAV 입출력, DSP, MIDI 파일 |
| Tracktion Engine | 지금은 넣지 않는다 | 이 도구는 오프라인 렌더링 전용이고 곡 구조는 JSON이 정한다. Tracktion의 Edit 모델은 같은 것을 한 벌 더 두는 셈이고 빌드가 무겁다. 실시간 재생, 복잡한 라우팅이 필요해지면 다시 본다. 2026-10-05: 실시간 재생은 엔진 안에 직접 만들었다 (7단계) |
| CLAP 호스팅 | 보류 | JUCE 8은 CLAP 호스팅을 내장하지 않는다. VST3와 AU가 먼저다 |
| SFZ | sfizz (BSD-2-Clause, `external/sfizz`)를 라이브러리로 넣는다 | 샘플 악기를 플러그인 없이 직접 연주한다. 프리휠링 모드로 오프라인에서 샘플 스트리밍을 기다린다 |
| 무료 악기 | VSCO 2 Community Edition (CC0, `external/vsco2-ce`, SFZ 브랜치) | 현악 합주(바이올린, 비올라, 첼로)와 콘트라베이스의 지속음, 스피카토, 피치카토, 트레몰로, 업라이트 피아노, 하프, 목관, 팀파니. 라이선스 제약이 없다 |
| 테스트용 플러그인 | 이 프로젝트 안에서 JUCE로 만든 사인파 신스 (VST3, AU) | 결정적이고 라이선스가 깨끗해 자동 테스트에 쓴다. 실제 제3자 플러그인 확인은 따로 한다 |
| JSON | `juce::JSON` | 오류에 줄과 칸이 나온다. 검증은 자체 검사기가 JSON 경로로 알린다 |

라이선스: JUCE 8은 AGPLv3와 상용의 이중 라이선스다. 로컬 도구로 쓰는 데는 문제가 없지만, 이 도구의 바이너리를
배포하려면 AGPL을 따르거나 상용 라이선스가 필요하다. 저장소에는 JUCE를 넣지 않고 소스만 받아 쓴다.

```text
  src/core/                      오류와 진단, 결정적 난수, JSON 도우미
  src/composition/               모델, 파싱, 검증 (JSON 경로가 붙은 오류, 오타 제안)
  src/timing/                    템포 맵 (고정, 변화, 선형 램프), 박과 초와 샘플의 변환
  src/performance/               휴머나이즈, 스윙, 악센트, 레가토 겹침
  src/automation/                컨트롤러 곡선 (linear, step, exponential, smooth)
  src/instruments/               레지스트리와 프로필, 내장 신스, SFZ(sfizz), 플러그인(VST3, AU)
  src/rendering/                 트랙 사슬(TrackChain), 오프라인 렌더러 (블록 단위, 샘플 정확도, 지연 보상)
  src/realtime/                  실시간 재생기 (오디오 콜백, 재생과 정지, 위치 옮기기, 뮤트와 솔로, 미터)
  src/mixer/, src/effects/       게인, 팬, 뮤트, 솔로, 버스와 센드, EQ, 컴프레서, 리버브, 리미터, 필터, 덕킹, 효과 매개변수와 센드의 곡선(Automation)
  src/analysis/                  피크, RMS, LUFS(ITU-R BS.1770-4), 클리핑
  src/midi/                      표준 MIDI 파일 내보내기
  src/cli/                       명령행
  schemas/                       composition.schema.json, instrument.schema.json
  instruments/registry.json      기본 악기 레지스트리 (내장 신스와 VSCO 2 CE)
  examples/                      piano_demo.json 등
  tests/                         단위 테스트, 명령행 끝까지 테스트
  testplugins/                   테스트용 VST3, AU 신스
```

## 4. 명령행

```bash
music-render validate song.json                 # 오류와 경고를 JSON으로 (경로, 메시지, 제안)
music-render render song.json --output song.wav [--sample-rate 48000] [--bit-depth 24] [--stems dir] [--seed N]
music-render inspect song.wav                   # duration, samples, peakDb, rmsDb, lufs, clipping
music-render export-midi song.json --output song.mid
music-render realtime song.json [--seconds 20] [--from 0] [--block-size 256] [--output out.wav]   # 실시간 재생기의 부하 측정
music-render instruments [--registry r.json]    # 레지스트리의 악기와 파일이 실제로 있는지
music-render plugins scan <경로>                 # VST3, AU 검색과 메타데이터 캐시
music-render plugins describe <플러그인>          # 매개변수 목록
```

표준 출력에는 기계가 읽을 JSON만 쓰고, 사람이 읽을 로그는 표준 오류로 보낸다. 종료 코드는 0 성공, 1 입력이나
렌더링 오류, 2 사용법 오류다.

## 5. 단계

### 1단계: JSON에서 WAV까지 (내장 신스)

- [x] JSON 파싱과 검증 (필수 필드, 범위, 모르는 필드 경고와 오타 제안, 음이름 `E4`, 줄과 칸이 붙은 JSON 문법 오류)
- [x] 템포 맵, 박에서 샘플로의 변환 (고정, 계단, 선형 램프의 닫힌 식과 역변환)
- [x] 연주 처리 (timingHumanizeMs, velocityHumanize, noteLengthHumanize, legatoOverlapMs, swing, accentPattern, humanizeSeed). 휴머나이즈 씨앗은 음표의 내용에서 얻어, 한 음을 고쳐도 다른 음의 흔들림은 그대로다
- [x] 내장 신스 (사인, 배음별 이중 감쇠 피아노, 패드, 현악, 베이스, 카플러스-스트롱 플럭, GM 드럼)
- [x] 오프라인 렌더러, WAV(16, 24비트 정수, 32비트 실수). 메타데이터를 넣지 않아 같은 오디오는 같은 바이트다
- [x] `validate`, `render`, `inspect`, `export-midi`, `instruments`, `version`
- [x] 단위 테스트(29건)와 명령행 테스트(69건): 샘플 수, 길이, 440 Hz, 블록 크기와 무관한 결정성, LUFS 교정(-20 dBFS 1 kHz = -20 LUFS), ffmpeg ebur128 과 0.3 LU 안

아직 없는 기능(믹서, 오토메이션, 아티큘레이션, 효과, 목표 LUFS)을 JSON 에 쓰면 무시하지 않고 "not implemented yet" 오류로 알린다 (`src/composition/Features.h`).

완료 기준: `music-render render examples/piano_demo.json --output output/piano_demo.wav`가 정상 WAV를 만들고,
같은 시드의 두 렌더링이 바이트 단위로 같다.

### 2단계: 플러그인 악기 (VST3, AU)

- [x] 검색과 메타데이터 캐시(`plugins scan`, 기본 `~/.cache/music-render/plugins.json`), 매개변수 목록(`plugins describe`), 상태 불러오기(`stateFile`, `state`)와 저장(`plugins save-state --set 이름=값`)
- [x] MIDI 전달과 오프라인 렌더링(`setNonRealtime`, 템포와 박자를 알리는 플레이헤드), 지연 보상 (지연 L 인 트랙을 L 샘플 당겨 섞는다)
- [x] 테스트용 신스 플러그인(`testplugins/TestSynth.cpp`, VST3)으로 같은 JSON 렌더링: 시작 샘플, 440 Hz, 진폭, 이름과 ID 로 지정한 매개변수, 프로그램, 상태 파일, 지연 1000 샘플이 지연 0 과 샘플까지 같다. 없는 플러그인은 `instrument` 오류이고 `fallback` 이 있으면 대신 쓴다
- [x] macOS 내장 AU(Apple DLS 신스)로 렌더링
- [x] 제3자 무료 플러그인 Dexed 1.0.1 (GPL-3.0, `external/plugins/` 에 받아 설치 없이): 검색(매개변수 2238개, 프로그램 32개), 피아노 데모 55초 렌더링, 두 번의 렌더링이 바이트까지 같다

플러그인 호스팅에는 JUCE 런타임이 필요하다. `HostSession` 을 main 의 지역 변수로 두고, 끝날 때 호스트를 먼저 내린 뒤 JUCE 를 닫는다
(정적 변수로 두면 프로세스가 끝날 때 죽는다).

### 3단계: 멀티트랙 믹서

- [x] 트랙 게인, 팬(스테레오 밸런스: 반대쪽을 cos 곡선으로 줄인다), 뮤트, 솔로, 마스터 버스(게인, 팬), 버스와 센드(프리, 포스트 페이더, `levelDb`)
- [x] 트랙별 스템(`--stems <폴더>`: 트랙 이름의 WAV, 버스는 `bus-<이름>.wav`, `master.wav`). 트랙 스템과 버스 스템의 합이 마스터와 같다 (32비트에서 1e-6 안)
- [x] 지연 보상을 정렬로 바꿨다: 트랙마다 지연선을 두어 모든 트랙을 가장 긴 지연에 맞춘 뒤 섞고, 앞의 그만큼을 버린다 (버스로 보내는 센드도 맞는다)

### 4단계: 오토메이션, CC, 아티큘레이션, SFZ

- [x] CC0..CC127, 피치 벤드(-1..1), 애프터터치 곡선 (linear, step, exponential, smooth). 악기로 보내는 곡선은 5ms 간격과 꺾이는 점에서 읽어 값이 바뀔 때 보낸다. 곡선의 마지막 점(페달을 떼는 시각 등)까지 곡으로 친다
- [x] 악기 프로필의 아티큘레이션: 키스위치(바뀔 때만, 같은 샘플의 음보다 먼저), SFZ 파일(파일마다 MIDI 채널), 프로그램, CC, 길이 배율, 벨로시티 보정, 레가토
- [x] 컨트롤러 처리 방식 `native`, `engine`, `both`, `ignore`. 엔진은 cc7(볼륨), cc11(익스프레션)을 (값/127)^2 게인으로, cc10 을 밸런스로, 다이내믹스 컨트롤러를 게인(dB 선형)과 밝기(2극 저역 통과, 로그 보간)로 처리한다
- [x] sfizz(정적 라이브러리)로 SFZ 연주. 프리휠링으로 오프라인에서 샘플 읽기를 기다리고, 결과는 결정적이다. 다이내믹스 곡선이 있으면 각 음을 레이어 벨로시티마다 울려 등전력으로 크로스페이드한다 (VSCO 처럼 벨로시티 레이어만 있는 SFZ 도 CC1 로 음색이 바뀐다)
- [x] 기본 레지스트리에 VSCO 2 CE: `violins`, `violas`, `celli`, `basses`, `violin-solo`(sustain, legato, staccato, spiccato, pizzicato, tremolo), `piano`(업라이트), `harp`, `timpani`, `flute`, `oboe`, `clarinet`. 샘플이 없으면 내장 신스로 대신한다
- [x] MIDI 내보내기에 컨트롤러 곡선

배운 것: 새 Apple clang 은 sfizz 에 딸린 atomic_queue 를 오류로 막아 sfizz 디렉터리에서만 그 경고를 끈다. 테스트가 파일 길이 밖을
재면 결과가 실행마다 달라진다 (측정 도우미가 범위를 검사한다).

### 5단계: 효과와 마스터링

- [x] EQ(RBJ 바이쿼드: 저역, 고역 차단 12 또는 24 dB/oct, peak, lowShelf, highShelf), 컴프레서(피드포워드, 스테레오 연동, 소프트 니), 게인
- [x] 리버브: 균일 분할 FFT 컨볼루션(오버랩 세이브, 분할 1024, 지연 1024)과 결정적으로 만드는 홀 IR(초기 반사 14개, 대역별 감쇠, 쌓이는 확산음, 폭) 또는 IR 파일. 알고리즘 리버브도 고를 수 있다
- [x] 룩어헤드 브릭월 리미터: 필요 게인의 [-L, +L] 최솟값을 다시 [-L, +L] 로 평균 내므로 넘침이 없다 (지연 2L)
- [x] 효과의 지연: 트랙 효과는 트랙 정렬이 받고, 버스와 마스터 효과는 전체 버퍼로 처리하며 지연만큼 당긴다
- [x] 목표 LUFS: 끝의 리미터 앞까지 처리해 재고, 게인을 맞추고, 리미터를 거친다. 리미터가 깎은 만큼 0.1 LU 안에 들 때까지 다시 맞춘다 (최대 네 번)
- [x] 트루 피크(4배 오버샘플)를 `render` 와 `inspect` 가 알린다

이로써 계획했던 기능이 모두 들어왔고 "not implemented" 로 막던 칸이 없어졌다. 단위 60건(검사 1154), 명령행 106건.

### 6단계: GUI

명령행 도구 위의 DAW 앱으로 이어진다. 계획과 진행은 [index.md](index.md)의 D 단계다.

### 7단계: 실시간 재생 (2026-10-05)

- [x] `buildTrackChain`: 악기, 연주 처리한 이벤트, 표현 단계, 트랙 효과, 페이더, 센드를 한 함수로 만든다. 오프라인 렌더러와 실시간 재생기가 함께 써서 두 결과가 갈라지지 않는다
- [x] `RealtimePlayer`: 오디오 콜백 크기와 상관없이 내부 블록(512)으로 나눠 처리한다. 재생, 정지(울리는 음을 끄고 서스테인을 뗀다), 위치 옮기기(앞의 컨트롤러, 프로그램, 피치 벤드를 다시 보낸다), 실시간 뮤트와 솔로(블록 하나에 걸친 게인 램프), 트랙과 마스터 미터, 모니터 게인
- [x] 오프라인과 다른 점: 버스와 마스터 효과는 블록 단위(지연을 되돌리지 않는다), 목표 LUFS 대신 모니터 게인을 끝의 리미터 앞에 둔다, 곡 끝 페이드아웃이 없다
- [x] `InstrumentContext.realtime`: sfizz 는 샘플을 기다리지 않고 스트리밍하고, 플러그인은 실시간 모드로 준비한다
- [x] 내장 신스의 목소리 난수를 음높이와 시작 샘플로 정한다 (앞의 음이 몇 개였든, 재생 위치를 옮겨도 같은 음은 같게 울린다)
- [x] `music-render realtime`: 실제 시간에 맞춰 블록을 부르고 평균과 최대 부하, 늦은 블록과 그 위치를 알린다
- [x] 시험: 실시간 결과가 오프라인 렌더와 샘플마다 1e-5 안에서 같다 (휴머나이즈, CC 곡선, 버스, 마스터 EQ 포함), 위치를 옮긴 뒤도 같다, 정지가 음을 끈다, 뮤트와 솔로와 모니터 게인. 단위 65건(검사 1183)

측정 (「붉은 별」 17트랙, 모두 SFZ, 콜백 256 샘플, 160초부터 15초): 준비 1.3초, 평균 부하 0.36, 늦은 블록 7개
(위치를 옮긴 첫 블록 4배, 코러스 머리의 음이 몰린 곳 1~2.5배). 첫 실행은 디스크 캐시가 비어 늦은 블록이 더 많다.
트랙을 여러 스레드로 나눠 처리하는 일은 D 단계의 성능 항목이다.

### 8단계: 전자 음악 도구 (2026-10-06)

계기: 드럼과 신스가 사이드체인으로 서로 걸리는 전자 음악 곡 「푸른 신호」.

- [x] 압축기 `sidechain`: 다른 트랙의 프리 페이더 신호를 검출기에 쓴다. 트랙 효과와 버스 효과 모두. 키 트랙을 먼저 처리하도록 트랙 순서를 정하고(`trackProcessOrder`), 오프라인 렌더러는 버스의 키를 곡 전체 길이로 모은다. 키를 받지 못한 블록은 무음으로 본다
- [x] 파서가 없는 키 트랙, 자기 자신, 서로를 키로 쓰는 고리를 오류로 막는다 (JSON 경로와 고칠 방법)
- [x] `delay`: 스테레오 또는 핑퐁, 되먹임 경로의 저역 차단과 고역 차단 (박에 맞추려면 `timeMs = 60000 / BPM * 박`)
- [x] 리미터 `truePeak`: 분석과 같은 4배 보간으로 샘플 사이 봉우리까지 깎는다 (지연 6샘플 더)
- [x] 내장 신스: 오실레이터마다 좌우 위치(유니즌을 벌린다), 필터 뒤 tanh 포화, CC74 가 필터를 연다(127 이 프리셋 그대로, 0 이 6옥타브 아래), 오실레이터 비율과 엔벨로프 계수를 음마다 한 번 계산
- [x] 프리셋: `supersaw`(톱니파 일곱), `saw-pad`, `edm-pluck`, `sub`, `saw-bass`, `lead`, `noise`(상승음), `edm-drums`(킥, 스네어, 39번 클랩, 808 식 하이햇, 크래시, 라이드)
- [x] 렌더링은 파일 없이(음량만 재기), 블록 사이에서 멈출 수 있다 (`RenderOptions.cancel`)
- [x] 시험: 키에서만 눌리는 압축기, 딜레이의 시각과 핑퐁, 렌더링에서 트랙과 버스의 펌핑, 뮤트한 키는 압축기가 없는 것과 같다, 참조 검사, 사이드체인이 있어도 실시간이 오프라인과 같다, 프리셋의 음높이와 폭과 CC74 와 드럼, 트루 피크 리미터. 단위 72건(검사 1212)

배운 것: 사이드체인 문턱은 키의 실제 크기에 맞춰야 한다. 킥 머리가 -1 dBFS 인데 문턱을 -26 dB 로 두었더니 킥 몸통이 박 내내
문턱을 넘어 화음과 베이스가 15~24 dB 눌린 채로 있었다 (펌핑이 아니라 그냥 작아진다). 문턱 -14 dB, 비율 12 로 바꾸니 킥 뒤
10 dB 에서 다음 박 전 2 dB 로 돌아온다. 펌핑의 깊이는 "사이드체인이 없는 렌더링과의 차"로 재야 한다 (박의 앞뒤만 비교하면 몸통이
남아 있는 늦은 쪽도 눌려 있어 얕게 나온다).

### 9단계: 빌드업 도구 (2026-10-14)

계기: 새 전자 음악 곡을 쓰기 전에 엔진을 넓힌다. 조사(사이드체인 버그 둘, 버스와 마스터에 시간에 따라 바뀌는 조절이 없음)를 따라
효과 매개변수 곡선, 필터, 박에 맞춘 덕킹, 센드 곡선, 박에 맞춘 딜레이를 더했다. 곡선은 효과 객체 안에 둔다
(`"automation": { "<매개변수>": [점, ...] }`, 점은 컨트롤러 곡선과 같은 `{beat, value, curve}`). 그래서 트랙, 버스, 마스터의 효과가 모두 같은
꼴이고, 앱의 편집(`withEffectParameter`)과 저장이 곡선을 그대로 지킨다.

- [x] 사이드체인 버그 1 (트랙 사이): 지연이 있는 트랙이 하나라도 있으면 키가 그만큼 늦게 왔다 (키를 트랙 정렬 뒤에서 읽었다).
  이제 키는 키 트랙의 정렬 전 프리 페이더 신호이고, 압축기가 자기 자리(악기 지연과 앞 효과의 지연)에 맞춰 키를 늦춘다. 키 트랙이 더 늦으면
  압축기 앞에서 소리를 늦추고 그만큼 트랙 지연이 는다 (`EffectChain::alignSidechains`, `alignTrackSidechains`). 오프라인과 실시간이 같은 함수를 쓴다
- [x] 같은 규칙을 버스와 마스터에도: 버스 사슬에서 압축기 앞의 효과(리버브의 1024 샘플)만큼 키를 늦춘다. 지금까지는 리버브 뒤의 키 압축기가
  21.3ms 먼저 눌렀다. 「푸른 신호」, 「잿빛 균열」, 「네온 비」, 「유리 회로」의 리버브 버스가 이 꼴이라 렌더링이 조금 달라진다 (아래 잰 값)
- [x] 사이드체인 버그 2: 마스터 압축기의 `sidechain` 이 검사를 지나고 아무 일도 하지 않았다. 이제 버스처럼 트랙의 정렬된 프리 페이더 신호를 키로
  받는다 (오프라인은 곡 전체 길이로 모으고, 실시간은 정렬된 트랙 신호에서). 없는 키 트랙은 검사가 오류로 알린다
- [x] 효과 매개변수 곡선: 매개변수 표(`ParameterInfo.automatable`)에 표시한 것만 곡선을 둘 수 있다 (모르는 매개변수, 곡선을 못 두는 매개변수,
  범위 밖의 값, 내려가는 박은 오류). 첫 점 앞은 첫 값, 마지막 점 뒤는 마지막 값이고, 곡선이 있으면 같은 이름의 고정값은 쓰지 않는다.
  곡선을 둘 수 있는 것: `gain.gainDb`, `filter.cutoffHz`, `filter.resonance`, `filter.mix`, `ducker.depthDb`, `ducker.mix`, `delay.mix`,
  `delay.feedback`, `reverb.mix`, `reverb.dryDb`, `reverb.wetDb`, `stereo.width`, `distortion.driveDb`, `distortion.mix`
- [x] 곡선은 곡 위치의 32 샘플 격자(템포 지도로 박을 잰다) 점에서 값을 재고 그 사이를 직선으로 잇는다 (`SampleLane`). 효과는 사슬이 넘기는
  곡 위치(트랙은 악기 지연을, 효과마다 앞 효과의 지연을 뺀 자리, 리버브의 크기는 나가는 소리의 자리)를 쓴다. 그래서 블록 크기, 실시간과 오프라인,
  위치 옮기기와 상관없이 같은 샘플이 나온다. 실시간에서는 그 자리를 시계와 곡 위치의 기록(`SongTimeline`)에서 읽는다 (아래 "9단계 고침").
  로그 매개변수(`cutoffHz`)는 점 사이를 로그 주파수로 잇는다 (linear 이면 옥타브마다 같은 시간). 효과의 곡선은 곡의 길이를 늘이지 않는다
- [x] `filter`: TPT 상태 변수 필터, 지연 없음. `mode` lowpass, highpass, bandpass, notch (곡선 없음), `slope` 12 또는 24 dB/oct (24 는 두 단),
  `cutoffHz` 20~20000 (기본 1000), `resonance` 0~1 (Q 0.7071 에서 10 까지 지수, 0 이면 저역과 고역 통과가 버터워스로 차단 주파수에서 -3 dB,
  1 이면 12 dB 저역 통과의 봉우리가 +20 dB), `mix` 0~1. 대역 통과는 가운데에서 0 dB. 곡선이면 격자 점마다 g = tan(pi fc / fs) 와 k = 1/Q 를
  구해 샘플마다 직선으로 잇는다 (계단 소리가 없다). `filterResponseDb` 가 같은 계수로 응답을 낸다
- [x] `ducker`: 키 트랙 없이 박마다 누르는 볼륨 셰이퍼. 주기는 `offsetBeats + k * rateBeats` 박에서 시작하고, `attackMs` 동안 0 dB 에서
  `depthDb` 로 (dB 직선), `holdMs` 동안 머문 뒤 `releaseBeats` 동안 남은 깊이 `depthDb * (1 - r)^curve` 로 돌아온다. 앞 주기가 아직 돌아오는
  중이면 더 깊은 쪽을 쓴다. 크기는 곡 위치만의 함수라 상태가 없다 (`duckerShape`). `depthDb` 와 `mix` 에 곡선을 두면 구간마다 펌핑을 켜고 끈다
- [x] 센드 크기 곡선: `sends[i].automation.levelDb` (-120~12 dB, -120 은 무음). 오프라인과 실시간이 같은 함수(`addSend`)로 정렬된 신호의 곡
  위치에서 격자 곡선을 읽는다. 앱의 센드 편집(`withSends`)은 곡선을 `SendSpec.levelLane` 에서 쓴다 (앞 센드를 지워도 곡선이 제 센드를 따라간다)
- [x] `delay.timeBeats` (1/64~16 박): 메아리는 언제나 그 박 수 앞의 소리다 (지금 박 - timeBeats 의 시각). 템포 램프에서는 길이를 격자마다 다시
  재고 4점 3차 보간으로 읽어 튀지 않는다. 지연선은 가장 느린 템포에서 필요한 길이로 미리 잡는다 (16초를 넘으면 곡을 읽을 때 오류).
  `timeMs` 와 함께 쓰면 경고하고 `timeBeats` 를 쓴다
- [x] 스키마, 검사 문구, `effectParameters` 표(`automatable`), 문서 저장의 왕복(곡선과 키 순서가 그대로), MIDI 내보내기(곡선과 상관없음)
- [x] 앱: 효과 추가 메뉴에 필터와 덕킹, 필터의 방식 칸, 새 매개변수의 한국어 이름과 도움말, 박 단위 표기, 곡선이 있는 매개변수는 이름 뒤에
  "(곡선)" 을 붙이고 손잡이를 끈다 (곡선 그리기는 아직 없다)
- [x] 시험: 곡선의 모양과 격자, 블록 크기와 상관없음, 바꿔 끼우기, 검사 오류, 필터 응답(네 방식, 두 기울기, 두 공진, 해석 응답과 0.05 dB 안),
  쓸기의 감쇠와 계단 없음, 덕킹이 닫힌 식과 1e-3 dB 안, 템포 램프와 가운데에서 시작해도 같은 샘플, timeBeats 의 메아리 자리(램프 포함 1 샘플 안),
  다른 곡선 매개변수, 트랙 지연과 키 트랙 지연이 있어도 킥 뒤 1~5ms 에 6 dB 넘게 누름(오프라인과 실시간), 마스터 사이드체인, 곡선 필터와 덕킹과
  게인과 센드 곡선과 박 딜레이가 든 곡의 실시간이 오프라인과 1e-5 안, 쓸기 가운데로 옮겨도 같음, apply 가 새 재생기와 같음, 문서 왕복과 MIDI.
  명령행 시험에 곡선 오류와 빌드업 곡의 결정성. 단위 145건(검사 3880, 새 시험 13건), 명령행 227건, CTest 10개 모두 통과

잰 값 (128 BPM, 시험 곡은 소리 없는 키 트랙과 톱니파 패드):

| 무엇 | 전 | 후 |
|---|---|---|
| 다른 트랙에 리버브(1024 샘플)가 있을 때 킥 뒤 1, 5, 20, 30ms 의 패드 크기 | -1.4, -1.4, -1.2, -8.6 dB | -6.7, -8.1, -8.5, -8.5 dB |

- 덕킹(깊이 -12, 어택 1ms, 유지 30ms, 돌아오기 0.5박, curve 1)을 버스에 걸고 1ms 창으로 재면 박 뒤 5ms -12.00, 100ms -8.44, 200ms -3.32,
  260ms -0.25, 300ms 0.00 dB (닫힌 식 -12.00, -8.47, -3.35, -0.28, 0.00)
- 마스터 고역 통과 24 dB 를 32박(15초) 동안 20 Hz 에서 1200 Hz 로: 16박에 55 Hz -37.0, 110 Hz -13.3 dB, 24박에 110 Hz -48.8, 440 Hz -3.6 dB,

- 센드 던지기: 12박에서 한 박만 딜레이 센드를 열면(나머지는 -120 dB) 10박은 무음, 12.5박 -27.9, 13.5박 -35.6 dBFS 로 메아리가 남는다
- 기존 곡을 새 엔진으로 다시 렌더링 (WAV, 고치기 전 엔진과 견줌): 「부서진 첨탑」은 같은 바이트. 리버브 뒤에 키 압축기가 있는 네 곡은 그 버스만
  달라진다. 「푸른 신호」를 스템으로 견주면 bus-verb 말고 트랙 스템과 다른 버스는 모두 같은 바이트이고, bus-verb 의 차이는 그 버스 크기의 -23.0 dB 다.
  마스터의 차이(마스터 크기 대비 RMS)는 「푸른 신호」 -42.8, 「잿빛 균열」 -48.8, 「유리 회로」 -48.8, 「네온 비」 -45.7 dB, 가장 큰 샘플 차이 0.028~0.054.
  목표 음량 게인, 적분 음량, 트루 피크는 다섯 곡 모두 그대로다 (예: 「푸른 신호」 +4.39 dB, -11.13 LUFS, -1.0 dBTP). 곡 JSON 과 커밋된 파일은 바뀌지 않는다

#### 9단계 이어서: 빌드업의 신스와 북 (2026-10-15)

계기: 조사에서 내장 신스의 피치 벤드가 ±2반음으로 묶여 있고(+1.95반음으로 쟀다), 신스 필터는 저역 통과만 되고, 북은 벤드와 조율을 받지

있는 북 소리를 고치면 그것을 쓰는 곡의 렌더링이 모두 바뀐다 (북 목소리는 언제나 그 길이에서 끊기므로 킥 하나하나가 달라진다). 그래서 새

#### 9단계 고침: 검토에서 나온 결함 (2026-10-15)

검토에서 오프라인 렌더, 재생 중의 실시간, 기존 곡은 맞았고, 실시간에서 재생하지 않는 동안과 반복의 되돌아가기, 앱의 두 칸이 틀렸다.

- [x] 멈춘 동안과 카운트인 동안 실시간 재생기는 블록마다 같은 곡 위치를 효과에 넘겼고, 효과는 블록 안에서 위치를 나아가게 했다. 그래서 곡선과
  덕킹이 블록마다 한 블록 분량을 되풀이했다 (박 위에 세워 두면 덕킹이 512 샘플마다 0 dB 에서 -12 dB 로 다시 떨어져 들려주는 음이 94 Hz 로
  떨렸다). 이제 재생하지 않는 블록은 곡선, 덕킹, 박 딜레이의 길이, 센드 곡선, 표현 단계(CC7, CC11, 다이내믹스)를 블록 내내 그 자리의 값에
  붙든다 (`BlockPosition.held`). 재생을 시작하면 그 값에서 이어진다
- [x] 반복의 되돌아가기 뒤 재생 지연(다른 트랙의 리버브면 1024 샘플) 동안은 아직 반복 끝 앞의 소리가 나오는데, 버스와 마스터의 효과, 센드 곡선,
  지연 효과 뒤의 트랙 효과는 되돌아간 자리에서 지연만큼 앞(반복 시작 앞)의 곡선 값을 읽었다. 반복 끝에서 끊는 게인 곡선이면 되돌아갈 때마다
  21ms 동안 끊기 전의 소리가 샜다. 이제 재생기가 시계(처리한 샘플 수)와 곡 위치의 기록(`SongTimeline`, 128 구간, 할당 없음)을 남기고, 지연된
  신호는 시계를 지연만큼 거슬러 제 곡 위치를 읽는다. 위치가 끊긴 블록에서는 위치를 따르는 효과(`Effect::followsPosition`)만 끊긴 자리에서 블록을
  나눠 처리한다 (나눈 조각은 버퍼를 가리키기만 해서 할당하지 않는다. 압축기처럼 위치를 쓰지 않는 효과는 나누지 않는다). 위치 옮기기도 같다:
  옮긴 뒤 지연 동안의 소리는 옮기기 전 자리의 곡선으로 나온다. 재생 중 끊김이 없으면 위치는 전과 같아 실시간이 오프라인과 같다는 시험이 그대로다
- [x] 효과의 위치는 이제 그 효과가 내보내는 소리의 자리다 (`setPosition` 은 앞 효과와 자기의 지연을 뺀 자리를 받는다). 지연과 곡선이 함께 있는
  효과는 컨볼루션 리버브 하나이고, 전에 리버브 안에서 빼던 분할 크기를 사슬이 뺀다 (오프라인 값은 같다)
- [x] 센드 곡선을 재생 중에 지우면 곡선의 마지막 값에서 고정값으로 블록 하나에 걸쳐 잇는다 (전에는 곡선 앞의 고정값에서 이어 튀었다)

  샘플, 센드 곡선을 지우면 0 에서 열린다. 옛 위치 계산을 흉내 내면 앞의 셋이 실패한다. 클럽 키트의 꽉 찬 목소리, 검사 오류와 경고(명령행),
  `--edit-test` 의 곡선 센드와 딜레이의 박 단위 시간. 단위 158건(검사 4083), 명령행 247건(새 검사 2건), `--edit-test` 187건
- 잰 값 (실시간 재생기, 블록 512, 시험 곡): 2박 위에 세운 채 들려준 패드(덕킹 -12 dB, 어택 1ms, 유지 30ms)를 덕킹이 없는 곡과 견주면,
  옛 위치 계산은 블록마다 앞 32 샘플이 -3.5 dB, 나머지가 -11.8 dB 로 블록 주기(94 Hz)로 출렁였고, 고친 뒤는 둘 다 0.00 dB 다 (그 자리의
  덕킹 크기는 0 dB). 반복 끝(7~8박)에서 -96 dB 로 끊는 마스터 게인 곡선과 다른 트랙의 리버브(지연 1024): 되돌아간 뒤 960 샘플의 크기가
  1~3초 대비 -1.4 dB(끊기 전의 소리가 샜다)에서 -97.4 dB 로 (7.4~8박은 둘 다 -98.8 dB)
- 기존 곡: 고친 엔진으로 다섯 곡을 다시 렌더링하면 위의 렌더링과 같은 바이트이고, 「푸른 신호」를 40초부터 12초 동안 `music-render realtime
  --output` 으로 받은 실시간 출력도 고치기 전 엔진과 같은 바이트다 (평균 부하 0.238 과 0.240, 다른 일이 도는 기계에서)
- 남긴 것: 알고리즘 리버브에서 곡선이 생기거나 사라지는 편집을 재생 중에 반영하면 JUCE 리버브의 10ms 크기 다듬기 때문에 그동안 원음이 두 배까지
  커질 수 있다 (버퍼를 비우지 않고 다듬기만 건너뛸 방법이 없다). 버스와 마스터 효과의 지연을 실시간에서 맞추지 않는 것은 전과 같다

### 10단계: 스템 없이 재는 렌더링 (2026-10-30)

곡을 잴 때마다 트랙, 버스, 마스터의 스템을 24비트 WAV 로 써서 `build/songs` 가 34 GB 까지 커졌고 디스크가 가득 찼다 (곡 하나에 1~2 GB).
스템은 크기를 재려고만 썼으므로, 엔진이 렌더링하면서 직접 재서 작은 JSON 으로 내놓는다.

- [x] `analysis/MixMeasure` 의 `StemMeter`: 이어지는 샘플을 받아 10 ms 칸의 전력과 사이드 ((L-R)/2) 전력, 8192 샘플 프레임 (5.9 Hz 칸) 의 12대역 에너지
  (경계 30, 60, 120, 250, 400, 500 Hz, 1, 2, 4, 8, 16 kHz) 를 모은다. 대역 에너지는 창을 씌운 스펙트럼의 몫으로 시간 영역의 에너지를 나눠 합이 전력과 같다
- [x] 오프라인 렌더러의 `RenderOptions::measure`: 트랙 (스템과 같은 자리, 페이더 뒤), 버스, 마스터 (목표 LUFS 를 맞춘 뒤) 마다 마디의 크기, 대역, 사이드와
  음표마다 머리의 크기 (0.03~0.25, 0.05~0.1, 0.25~0.35 초) 와 길이. 마디는 박자 지도와 템포 지도로 곡 끝 (꼬리 포함) 까지
- [x] 명령행 `render --measure <file.json>` 과 읽는 도구 `tools/mix-report.py` (구간 크기, 선율 대 나머지, 대역 몫, 저역, 마디 크기, 음 크기, 사이드)
- [x] 시험: 사인파의 전력, 대역 (700 Hz 는 500~1000 Hz 에 99% 넘게, 80 Hz 는 60~120 Hz 에 97% 넘게), 사이드 (같은 채널 0, 반대 위상 전부),
  렌더링의 마디 경계와 음 머리와 길이 (단위 3건), 명령행 6건 (모든 스템, 마디 수, 음표, 스템 파일 없음, 크기 200 KB 아래, 마스터 크기가 리포트와 0.5 dB 안)
- 잰 값: 「잔해의 노래」 (53초 루프, 트랙 12) 의 스템은 273 MB, 측정 JSON 은 48 KB 다. 스템을 numpy 로 잰 값과 구간 크기 0.0~0.2 dB, 400 Hz 위 선율 대 나머지
  0.2~0.3 dB, 대역 몫 0.1~0.2 dB, 마디 크기 0.0~0.2 dB, 사이드 대 미드 0.0 dB 차이. 첫 판의 2048 샘플 프레임은 80 Hz 가 30~60 Hz 대역으로 새어 8192 로 늘렸다

## 6. 첫 곡: 홍보 영상 음악 (2026-10-05)

엔진으로 첫 실제 곡(현악, 목관, 호른, 합창)을 썼다. 작곡 생성기가 Composition JSON 을 쓰고 엔진이 렌더링한다.
첫 판의 현악 48마디는 `examples/orchestral_demo.json` 으로 남겼다. 전체 곡 3분 52초와 영상판 64초, 둘 다 -16 LUFS, 피크 -1 dBFS.

곡을 쓰다 엔진에 더한 것:

- [x] `sfzRegionOpcodes`: SFZ 파일을 문자열로 읽어 모든 `<region>` 에 옵코드를 덧붙이고 원래 경로 기준으로 불러온다 (sfizz `loadSfzString`).
  현악 프로필은 `ampeg_attack_oncc102=0.45` 로 CC102 가 공격 시간을 늘리고, 아티큘레이션이 CC102 를 보낸다 (sustain 0.09초, legato 0.25초).
  VSCO 지속음 샘플의 1ms 공격 때문에 레가토 선율의 음마다 활 공격이 새로 들리던 것을 줄인다
- [x] 기본 레지스트리의 팀파니에 `roll` 아티큘레이션 (TimpaniRolls.sfz)
- [x] `stereo` 효과: 무대 위치(pan, 등전력)와 폭(width, 미드 사이드). 악기를 무대에 앉히고 두 버스(짧은 무대 반사, 긴 홀 꼬리)로 앞뒤를 둔다
- [x] 기본 레지스트리에 VSCO 의 `percussion`(GM 배치 타악기: 큰북, 서스펜디드 심벌 스웰, 벨트리, 공 등)과 `glockenspiel`
- [x] 기본 레지스트리에 Sonatina Symphonic Orchestra(CC Sampling Plus 1.0): `choir`, `choir-large`, `horn`, `horns`, `oboe-solo`, `clarinet-solo` (2026-10-10 `staccato` 아티큘레이션, 기본은 `sustain`), `flute-solo` (2026-10-10), `cor-anglais`, `celeste`.
  VSCO 2 CE 에는 합창이 없다. `build.sh --samples` 가 필요한 폴더만 `external/sso` 에 받는다 (약 560MB, 위치는 `MUSIC_RENDER_SSO`)
- [x] `sfzRegionOpcodes` 가 `#include` 로 들어오는 리전에도 붙는다 (포함 파일을 최상위 파일의 폴더 기준으로 펼친 뒤 덧붙인다). SSO 는 리전을 포함 파일에 둔다

측정으로 고친 것: 콘트라베이스, 솔로 바이올린, 팀파니가 다른 악기보다 10 dB 넘게 작아 올렸고, 피아노 왼손과 저역(50~300 Hz)이 꽉 차 피아노
저역 차단과 마스터 로우 셸프를 넣었다. 4~8 kHz 가 어두운 것은 필터가 아니라 VSCO 녹음의 음색이라 (스템별로 쟀다) 마스터 하이 셸프만 더했다.
후반이 깨지던 것은 리미터였다: 리미터 없이 렌더링해 재 보니 -14 LUFS 에서 가장 큰 곳을 2.7 dB 깎아야 했다. 목표를 -16 LUFS 로 내렸다 (0.7 dB 안).
2절 뒤 콘트라베이스가 첼로 옥타브에 있어 절정의 저역이 비던 것, 합창 선율의 공격이 늦던 것(SSO 합창은 벨로시티가 공격 시간이다)도 스템으로 찾아 고쳤다.
귀로 듣는 판정은 저자 몫이다.

## 7. 테스트

`./build.sh`가 빌드한 뒤 CTest로 단위 테스트와 명령행 테스트를 돌린다. 렌더링 테스트는 파일이
있는지만 보지 않고 샘플 수, 길이, 주파수, 레벨을 잰다. 같은 실패가 세 번 반복되면 멈추고 저자에게 알린다.
